> 이 글은 실제 협업 프로젝트에서 겪은 사고가 아니라, 이번 주 배운 명령어들을 하나의 흐름으로 이어보기 위해 **직접 만든 가상의 연습 시나리오**를 바탕으로 작성했습니다.

## 들어가며 (Situation)

이번 주에 `git init`, `git add`, `git commit`, `git branch`, `git checkout`, `git push`, `git pull`, `git merge`, `git reset`, `git revert`까지 Git과 GitHub의 기본 명령어 10개를 하나씩 배웠습니다.

그런데 각 명령어의 "사용법"은 외웠지만, 이 명령어들이 실제로 어떤 순서로 이어지는지는 감이 잘 안 잡혔습니다. 수업에서는 명령어를 하나씩 따로 설명해줬을 뿐, "지금 이 시점에 왜 이 명령어를 써야 하는지"는 직접 이어 붙여봐야 이해될 것 같았습니다. 그래서 실제 협업 프로젝트가 아니라, 혼자서 처음부터 끝까지 재현해볼 수 있는 가상의 개인 프로젝트 시나리오를 만들어보기로 했습니다.

## 문제 상황 (Task)

연습용 로컬 저장소 하나로 아래 흐름을 전부 재현하는 것이 목표였습니다.

1. 저장소를 만들고 첫 커밋을 남긴다.
2. 새 기능은 `main`을 건드리지 않고 별도 브랜치에서 작업한 뒤 병합한다.
3. GitHub에 push한다.
4. **아직 push하지 않은** 로컬 커밋 실수는 `reset`으로 정리한다.
5. **이미 push된** 커밋 실수는 `revert`로 되돌린다.

제약 조건은 두 가지였습니다.

- 실제 협업 중인 저장소가 아니라 실습용 저장소여야 마음 놓고 실수할 수 있다.
- 단순히 "명령어를 다시 나열"하는 게 아니라, **각 단계에서 왜 다른 대안 대신 그 명령어를 골랐는지**까지 설명할 수 있어야 진짜로 이해했다고 볼 수 있었습니다.

## 해결 과정 (Action)

### 1. 저장소 초기화

| 명령어 | 언제 쓰나 |
|---|---|
| `git init` | 새 폴더를 Git 저장소로 만들고 싶을 때 (딱 한 번만 실행) |

폴더 안에 숨김 폴더(`.git`)가 생기고, 여기에 앞으로의 모든 기록이 저장됩니다.

### 2. 왜 스테이징 단계를 거치는가

파일을 수정했다고 바로 기록(커밋)되는 게 아니라, "이번 기록에 포함할 파일"을 먼저 골라야 합니다.

| 명령어 | 언제 쓰나 |
|---|---|
| `git add 파일명` | 특정 파일 하나만 이번 기록에 포함하고 싶을 때 |
| `git add .` | 수정한 파일을 전부 이번 기록에 포함하고 싶을 때 |

> 왜 굳이 골라야 할까요? 파일 두 개를 고쳤는데 그중 하나만 아직 완성이 안 됐다면, 완성된 것만 먼저 스테이징해서 기록할 수 있기 때문입니다. `add` 없이 바로 `commit`이 됐다면 미완성 코드까지 기록에 섞여 들어갔을 겁니다.

첫 파일을 스테이징 후 커밋했습니다.

```bash
git add index.html
git commit -m "초기 페이지 구조 작성"
```

### 3. 왜 main에서 바로 작업하지 않고 브랜치를 나눴는가

새 기능(다크 모드 버튼)을 추가하려던 시점에, `main`에서 바로 작업할지 브랜치를 새로 팔지 고민했습니다.

| | main에서 바로 작업 | 브랜치를 나눠 작업 |
|---|---|---|
| 작업 중 문제 발생 시 | `main` 자체가 불안정해짐 | `main`은 안전하게 유지됨 |
| 완성 전 되돌리기 | 이미 섞인 커밋에서 골라내야 함 | 브랜치를 그냥 지우면 됨 |
| 다른 작업과의 충돌 | 바로 영향받음 | 병합 시점에만 영향받음 |

이 비교 때문에 새 기능은 브랜치를 나눠 작업하기로 했습니다.

| 명령어 | 언제 쓰나 |
|---|---|
| `git branch 브랜치명` | 새로운 브랜치를 만들고 싶을 때 |
| `git checkout 브랜치명` | 만들어둔 브랜치로 이동(전환)하고 싶을 때 |

<pre class="mermaid">
flowchart TD
    M1["main: 초기 커밋"] --> M2["main: (변경 없음)"]
    M1 -- "git branch feature" --> B1["feature: 다크 모드 CSS 작성"]
    B1 --> B2["feature: 버튼 연결"]
</pre>

### 4. GitHub와 연결하기

로컬에서만 있던 기록을 원격 저장소와 주고받을 차례였습니다.

| 명령어 | 언제 쓰나 |
|---|---|
| `git push` | 내 Local Repository의 기록을 GitHub에 올리고 싶을 때 |
| `git pull` | GitHub에 있는 최신 기록을 내 컴퓨터로 받아오고 싶을 때 |

<pre class="mermaid">
flowchart LR
    L["Local Repository"] -- "git push" --> Rmt["원격 저장소 (GitHub)"]
    Rmt -- "git pull" --> L
</pre>

### 5. merge로 다시 합치기

feature 브랜치에서 기능이 완성된 뒤, main으로 이동해 병합했습니다.

| 명령어 | 언제 쓰나 |
|---|---|
| `git merge 브랜치명` | 다른 브랜치의 기록을 지금 브랜치로 합치고 싶을 때 |

<pre class="mermaid">
flowchart LR
    M2["main: 초기 커밋"] -- "git merge feature" --> M3["main: 다크 모드 기능 병합됨"]
    B2["feature: 버튼 연결"] --> M3
</pre>

### 6. 시행착오 1 — 아직 push하지 않은 커밋 실수: reset

병합 직후, 테스트용으로 넣었던 `console.log`가 커밋에 그대로 남아있는 걸 발견했습니다. 이 커밋은 아직 GitHub에 push하기 전이라, 기록을 정리해도 문제가 없는 상황이었습니다.

| 옵션 | 결과 |
|---|---|
| `--soft` | 커밋만 취소, 변경 내용은 스테이징 영역에 보존 |
| `--mixed` | 커밋과 스테이징 취소, 변경 내용은 작업 디렉터리에 보존 (기본값) |
| `--hard` | 커밋과 변경 내용 전부 삭제 |

**첫 번째 시행착오**는 여기서 나왔습니다. 별생각 없이 `git reset --hard`를 실행했더니, `console.log`만 지워지길 바랐는데 같은 커밋에 들어있던 정상적인 다크 모드 CSS 수정 내용까지 통째로 사라졌습니다. 결국 `--soft` 옵션으로 다시 시도해, 코드는 스테이징 영역에 남긴 채 커밋 기록만 취소하고 `console.log`만 지운 뒤 재커밋했습니다.

```bash
git reset --soft HEAD~1
# console.log 줄만 삭제
git add .
git commit -m "디버깅 코드 제거 후 재커밋"
```

### 7. 시행착오 2 — 이미 push된 커밋 실수: revert

이후 설정 파일에 오타를 넣은 채로 push까지 마쳐버렸습니다. 이미 GitHub에 올라간 기록이라 `reset`으로 되돌리면, 나중에 이 저장소를 pull 받는 사람의 기록과 어긋날 수 있는 상황이었습니다. 그래서 기존 기록은 그대로 둔 채 변경만 취소하는 `revert`를 선택했습니다.

```bash
git revert HEAD
```

**두 번째 시행착오**는 revert 실행 후 자동으로 열린 커밋 메시지 편집기였습니다. `commit -m`으로 메시지를 바로 넣는 데 익숙해져 있어서 편집기가 뜨자 멈춘 줄 알았는데, Git이 기본 메시지를 미리 채워주니 그대로 저장하고 닫으면 된다는 걸 확인했습니다.

flowchart LR
    C1["커밋: 오타 있는 설정 파일"] -- "git revert" --> C2["커밋: 오타 취소하는 새 커밋"]
</pre>

## 결과 (Result)

| 항목 | Before (연습 전) | After (연습 후) |
|---|---|---|
| 10개 명령어를 하나의 흐름 안에서 사용해본 경험 | 0개 (사용법만 따로 암기) | 10개 전부 실제로 사용 |
| 로컬 전용 실수 처리 방법 | `--soft`/`--mixed`/`--hard` 중 뭘 써야 할지 몰랐음 | `--hard` 시행착오 1회 후 `--soft`로 정상 처리 |
| 이미 push된 실수 처리 방법 | reset과 revert를 구분하지 못함 | `revert`로 충돌 없이 해결 |
| 전체 흐름 재현 시행착오 | - | 2회 발생, 2회 모두 해결 (미해결 0건) |

전체 흐름에서 브랜치는 1개 생성해 1회 병합했고, 시행착오 2회 모두 그 자리에서 해결해 최종적으로 되돌리기까지 포함한 흐름을 처음부터 끝까지 재현하는 데 성공했습니다. 다만 10개 명령어 중 망설임 없이 바로 재현할 수 있었던 건 8개(80%)였고, 나머지 2개(`merge`가 fast-forward로 처리될지 여부 판단, `revert`의 커밋 메시지 편집기 화면)는 이번에 처음 겪어보며 헷갈렸던 부분입니다.

가장 크게 배운 점은, 명령어를 따로따로 외우고 있을 때는 몰랐던 "지금 이 상황에 왜 이 명령어를 써야 하는가"가 하나의 흐름 안에서 실수를 직접 겪어보니 훨씬 분명해졌다는 것이었습니다.

## 더 학습하면 좋은 개념

- **git reflog** — `reset --hard`로 사라진 것처럼 보이는 커밋도 일정 기간 `reflog`에 남아있어 복구할 수 있습니다. 실수해도 되돌릴 방법이 있다는 걸 알면 reset을 훨씬 덜 두려워하며 쓸 수 있습니다.
- **merge conflict 해결** — 이번 연습에서는 충돌 없이 병합됐지만, 같은 파일을 여러 브랜치에서 고치면 충돌이 납니다. 협업에서는 피할 수 없는 상황이라 미리 익혀둘 필요가 있습니다.
- **.gitignore** — 애초에 `console.log` 같은 디버깅 코드나 민감한 설정 파일이 커밋되지 않도록 예방하는 설정입니다. 되돌리기보다 예방이 항상 더 쉽다는 걸 이번 연습에서 느꼈습니다.
- **interactive rebase (`git rebase -i`)** — 여러 커밋을 합치거나 순서를 바꾸는 등, 아직 공유하지 않은 기록을 더 세밀하게 편집하는 방법입니다. reset보다 정교한 "기록 다듬기" 도구입니다.
