> 이 글은 특정 사고 하나를 다루기보다, 팀에서 반복적으로 마주친 여러 충돌 유형을 **레퍼런스 문서 목적**으로 정리한 글입니다. 그중 "같은 파일/같은 줄 수정" 충돌은 실제로 겪은 상황을 그대로 담았고, 나머지 유형은 공식 문서와 팀 경험을 바탕으로 정리했습니다.

## 들어가며 (Situation)

여러 명이 각자 브랜치를 따서 기능을 개발하고 `main`에 병합하는 방식으로 협업하고 있었습니다. 브랜치가 늘어나고 병합 빈도가 잦아지면서 충돌(conflict)이 자주 발생했는데, 문제는 **팀원마다 충돌을 다르게 처리**한다는 점이었습니다.

어떤 팀원은 충돌 마커를 지우다가 코드 일부를 통째로 날려버렸고, 어떤 팀원은 당황해서 `git push --force`를 실행했다가 다른 사람의 커밋을 덮어써 버린 적도 있었습니다. "충돌이 나면 일단 겁부터 난다"는 반응이 반복되길래, 대표적인 충돌 유형과 유형별 안전한 해결 절차를 정리해두기로 했습니다.

## 문제 상황 (Task)

"브랜치 충돌"이라고 뭉뚱그려 부르지만, 실제로는 원인이 서로 다른 여러 상황이 섞여 있었습니다.

- 같은 파일의 같은 줄을 두 브랜치에서 각각 수정한 경우
- `rebase` 중에 커밋 하나하나마다 반복해서 충돌이 나는 경우
- 한쪽은 파일을 수정했는데 다른 쪽은 그 파일을 삭제하거나 이름을 바꾼 경우
- `package-lock.json`처럼 자동 생성되는 파일에서 나는 충돌

원인이 다르면 해결 방법도 달라야 하는데, 이 구분 없이 "충돌 마커 지우고 아무거나 남기기" 식으로 대응하다 보니 코드가 깨지거나 남의 작업이 사라지는 사고로 이어졌습니다. 이 글의 목표는 **각 유형을 구분하고, 유형별로 안전하게 해결하는 절차를 표준화**하는 것입니다.

## 해결 과정 (Action)

### 1. 충돌 유형 한눈에 비교

먼저 실무에서 자주 만나는 충돌 유형을 원인과 권장 해결법 기준으로 정리했습니다.

| 충돌 유형 | 발생 원인 | 권장 해결 방법 |
|---|---|---|
| 같은 파일/같은 줄 수정 | 두 브랜치가 동일한 라인을 서로 다르게 변경 | 충돌 마커 확인 후 의도를 파악해 직접 병합 |
| rebase 중 반복 충돌 | 커밋을 하나씩 재적용하며 매 커밋마다 비교 | `git rebase --continue` / `--skip` / `--abort` 구분 사용 |
| 파일 삭제/이름 변경 충돌 | 한쪽은 파일 유지·수정, 다른 쪽은 삭제·이름 변경 | `git status`로 상태 확인 후 유지 여부 협의 |
| lock 파일 충돌 | 의존성 설치 시 자동 생성되는 파일이 각자 다르게 갱신됨 | 수동 병합 대신 재설치로 파일 재생성 |

### 2. 같은 파일/같은 줄 수정 충돌 — 실제로 겪은 상황

가장 흔하고, 실제로 직접 겪었던 유형입니다. 두 브랜치에서 같은 설정값을 서로 다르게 고쳤을 때 `main`에 merge하면서 충돌이 났습니다.

<pre class="mermaid">
flowchart LR
    M["main"] --> B1["feature/a<br/>MAX_RETRY = 5"]
    M --> B2["feature/b<br/>MAX_RETRY = 3"]
    B1 --> Merge{"main으로 merge"}
    B2 --> Merge
    Merge -->|같은 줄 수정| Conflict["충돌 발생"]
</pre>

실제로 만난 충돌 마커는 다음과 같은 형태였습니다.

```js
<<<<<<< HEAD
const MAX_RETRY = 3;
=======
const MAX_RETRY = 5;
>>>>>>> feature/retry-limit
```

**시행착오**는 여기서 나왔습니다. 처음에는 `<<<<<<<`, `=======`, `>>>>>>>` 마커 자체를 지우는 데만 신경 쓰다가, 마커 한 줄을 실수로 남긴 채 커밋해서 빌드가 깨진 적이 있었습니다. 이후로는 아래 순서를 팀 규칙으로 정했습니다.

1. 마커 사이의 **양쪽 코드 의도**를 먼저 파악한다 (어느 브랜치의 어떤 작업 때문에 생긴 값인지).
2. 마커를 지우고 실제로 반영할 코드만 남긴다.
3. 마커가 하나도 남지 않았는지 `git diff`로 다시 확인한다.
4. 반드시 **로컬에서 실행/테스트한 뒤** 커밋한다.

```bash
git add <해결한 파일>
git commit  # merge 커밋 메시지는 자동으로 채워짐
```

### 3. rebase 중 반복 충돌

`merge` 대신 `rebase`를 쓸 때는 충돌 양상이 다릅니다. rebase는 커밋을 하나씩 재생(replay)하기 때문에, 커밋이 여러 개면 **커밋마다 충돌이 반복해서 발생**할 수 있습니다.

<pre class="mermaid">
sequenceDiagram
    participant Dev as 개발자
    participant Git as git rebase
    Dev->>Git: git rebase main
    Git-->>Dev: 커밋1 재적용 중 충돌
    Dev->>Git: 충돌 해결 후 git add, git rebase --continue
    Git-->>Dev: 커밋2 재적용 중 충돌
    Dev->>Git: 다시 해결 후 git rebase --continue
    Git-->>Dev: 모든 커밋 재적용 완료
</pre>

여기서 팀원들이 자주 헷갈려한 것이 `--continue`, `--skip`, `--abort`의 차이였습니다.

| 명령어 | 상황 | 결과 |
|---|---|---|
| `git rebase --continue` | 충돌을 해결하고 계속 진행하고 싶을 때 | 현재 커밋 재적용을 마치고 다음 커밋으로 진행 |
| `git rebase --skip` | 이 커밋 자체를 반영하지 않아도 될 때 | 현재 커밋을 건너뛰고 다음 커밋으로 진행 |
| `git rebase --abort` | 도저히 정리가 안 되거나 잘못 시작했을 때 | rebase 이전 상태로 완전히 되돌림 |

한 팀원은 충돌이 계속 반복되자 당황해서 무작정 `--skip`을 눌렀는데, 그 결과 자신이 작업한 커밋 하나가 통째로 사라진 채 rebase가 끝나버린 적이 있습니다. **의미 있는 커밋인데 반영이 안 됐다면 `--skip`이 아니라 충돌을 실제로 해결하고 `--continue`를 써야 한다**는 걸 이 사건으로 확인했습니다.

### 4. 파일 삭제/이름 변경 충돌

한쪽 브랜치에서 파일을 수정하는 동안 다른 브랜치에서 같은 파일을 삭제하거나 이름을 바꾼 경우입니다. 이때는 텍스트 충돌 마커가 아니라 `git status`에 아래처럼 표시됩니다.

```bash
both modified:      src/utils.js
deleted by us:      src/legacy-helper.js
deleted by them:    src/legacy-helper.js
```

이 유형은 코드 내용을 병합하는 문제가 아니라 **"이 파일을 유지할지 말지"를 판단하는 문제**이기 때문에, 임의로 결정하지 않고 왜 삭제/이름 변경이 있었는지 커밋 이력이나 담당자에게 확인한 뒤 처리하도록 규칙을 정했습니다.

```bash
git log --diff-filter=D -- src/legacy-helper.js  # 언제, 왜 삭제됐는지 확인
```

### 5. lock 파일 충돌

`package-lock.json`, `yarn.lock`처럼 의존성 설치 시 자동 생성되는 파일은 두 브랜치에서 서로 다른 시점에 `npm install`을 실행하면 거의 항상 충돌이 납니다. 이 파일은 사람이 직접 읽고 병합하도록 만들어진 파일이 아니기 때문에, 마커를 손으로 고치는 대신 **재생성**하는 방법을 택했습니다.

```bash
git checkout --theirs package-lock.json  # 또는 삭제
npm install  # lock 파일을 다시 생성
git add package-lock.json
```

## 결과 (Result)

정량적으로 측정한 지표는 아직 없지만, 정리 이후로 눈에 띄게 달라진 부분은 있었습니다.

| 항목 | Before | After |
|---|---|---|
| 충돌 대응 방식 | 팀원마다 제각각 (마커 임의 삭제, 무작정 force push) | 유형별 표준 절차를 참고해서 대응 |
| lock 파일 충돌 | 수동으로 병합 시도하다가 의존성 꼬임 발생 | 재설치로 재생성, 병합 시도 안 함 |
| rebase 커밋 유실 사고 | `--skip` 오남용으로 커밋 사라짐 | `--continue`/`--skip`/`--abort` 구분 후 재발 없음 |

가장 크게 배운 점은, **"충돌"이라는 현상은 같아 보여도 원인이 다르면 올바른 해결 절차도 완전히 다르다**는 것이었습니다. 특히 자동 생성 파일은 애초에 "병합"이 아니라 "재생성" 대상이라는 걸 구분하게 된 게 가장 실질적인 변화였습니다.

## 더 학습하면 좋은 개념

- **3-way merge 알고리즘** — Git이 충돌 여부를 판단할 때 두 브랜치뿐 아니라 공통 조상(base) 커밋까지 함께 비교합니다. 이 원리를 알면 왜 어떤 변경은 자동 병합되고 어떤 변경은 충돌로 표시되는지 이해할 수 있습니다.
- **git rerere** — "reuse recorded resolution"의 약자로, 한 번 해결한 충돌 패턴을 기록해뒀다가 같은 충돌이 다시 나오면 자동으로 재적용해주는 기능입니다. rebase처럼 같은 충돌이 반복되는 상황에서 특히 유용합니다.
- **git merge vs git rebase 전략 비교** — 두 방식은 충돌 발생 시점과 히스토리 형태가 다릅니다. 팀 컨벤션으로 어느 쪽을 기본으로 쓸지 정해두면 이번 글에서 다룬 rebase 반복 충돌 자체를 줄일 수 있습니다.
- **`--force-with-lease`** — 강제 push가 꼭 필요할 때, 다른 사람이 그사이 push한 내용을 덮어쓰지 않도록 안전장치를 걸어주는 옵션입니다. `--force`를 습관적으로 쓰는 문제를 예방합니다.
- **작은 단위로 자주 커밋/병합하기** — 충돌 해결법을 아는 것만큼 중요한 건 애초에 충돌 범위를 줄이는 협업 습관입니다. 브랜치 수명이 짧을수록 충돌 가능성도 줄어듭니다.
