> 이 글은 실제 프로젝트 사고가 아니라, **되돌리기 명령어를 이해하기 위해 직접 만들어본 연습 시나리오**를 바탕으로 작성했습니다.

## 들어가며 (Situation)

이번 주에 `git init`부터 `git commit`, `git push`, `git merge`까지 Git의 기본 흐름을 배웠습니다. 그런데 실습 중 커밋을 몇 번 잘못 남기면서, "이걸 어떻게 되돌리지?"라는 질문이 자연스럽게 생겼습니다.

그래서 일부러 아래와 같은 연습 시나리오 두 가지를 만들어보고, 각각 어떤 명령어로 해결하는 게 맞는지 직접 비교해봤습니다.

## 문제 상황 (Task)

연습용 저장소에서 다음 두 가지 실수를 재현했습니다.

1. **아직 push하지 않은 로컬 커밋**에 테스트용으로 넣었던 `console.log` 디버깅 코드가 그대로 들어가 버렸습니다.
2. **이미 GitHub에 push까지 마친 커밋**에서, 오타가 있는 설정 파일을 커밋해버렸습니다.

두 상황 모두 "커밋을 취소하고 싶다"는 점은 같았지만, **아직 아무도 이 기록을 받아가지 않았는지**가 달랐습니다. 이 차이 때문에 같은 명령어를 그대로 쓸 수 없다는 걸 알게 됐고, `git reset`과 `git revert` 중 어느 쪽을 써야 하는지가 이번 연습의 핵심 과제였습니다.

## 해결 과정 (Action)

### 1. 두 명령어의 동작 방식 비교

먼저 둘의 차이를 표로 정리하고 시작했습니다.

|구분 | git reset | git revert|
|---|---|---|
|하는 일| 브랜치 위치를 과거 커밋으로 옮김| 특정 커밋을 취소하는 새 커밋을 추가함|
|기존 커밋 기록| 가려지거나 사라짐| 그대로 남음|
|공유된 기록에 사용| 위험함 (기록이 어긋남)| 안전함 (기록을 추가만 함)|

|되돌리고 싶은 커밋이 이미 push되어 공유 중인가?| 선택할 명령어|
|---|---|
|아니오 (내 로컬에만 있음)| `git reset`|
|예 (다른 사람도 받아간 기록)| `git revert`|

### 2. 상황 1 — 아직 push 안 한 커밋: git reset

디버깅 코드가 들어간 커밋은 아직 저 혼자만 가지고 있었기 때문에, 기록을 아예 정리해도 문제가 없었습니다. 다만 `reset`에 세 가지 옵션(`--soft`, `--mixed`, `--hard`)이 있다는 걸 알고 나서, 어떤 걸 써야 할지 한 번 더 고민이 필요했습니다.

|옵션 | 결과|
|---|---|
|`--soft`| 커밋만 취소, 변경 내용은 스테이징 영역에 보존|
|`--mixed`| 커밋과 스테이징 취소, 변경 내용은 작업 디렉터리에 보존 (기본값)|
|`--hard`| 커밋과 변경 내용 전부 삭제|

<pre class="mermaid">
flowchart LR
    C1["커밋 1"] --> C2["커밋 2"] --> C3["커밋 3<br/>(console.log 포함)"]
    C3 -. "git reset --soft 커밋2" .-> S["커밋 2로 이동<br/>+ 코드는 스테이징에 보존"]
    C3 -. "git reset --hard 커밋2" .-> H["커밋 2로 이동<br/>+ 코드까지 전부 삭제"]
</pre>

**첫 번째 시행착오**는 여기서 나왔습니다. 처음에는 별생각 없이 `git reset --hard 커밋2`를 실행했는데, `console.log`만 지우면 됐던 게 아니라 같은 커밋에 함께 들어있던 정상적인 코드 수정 내용까지 통째로 사라져버렸습니다. 결국 `--soft` 옵션으로 다시 시도해서, 코드는 스테이징 영역에 남긴 채 커밋 기록만 취소하고 `console.log`만 지운 뒤 다시 커밋하는 방식으로 해결했습니다.

```bash
git reset --soft 커밋2
# 필요 없는 console.log 줄만 수정
git add .
git commit -m "디버깅 코드 제거 후 재커밋"
```

### 3. 상황 2 — 이미 push된 커밋: git revert

오타가 있는 설정 파일은 이미 `git push`로 GitHub에 올라간 상태였습니다. 만약 여기서도 `reset`을 쓰고 강제로 다시 push했다면, 같은 브랜치를 pull 받은 다른 사람의 기록과 어긋나면서 충돌이 발생했을 상황이었습니다. 그래서 이번에는 기존 기록을 건드리지 않는 `git revert`를 선택했습니다.

```bash
git revert 커밋5
```

<pre class="mermaid">
flowchart LR
    C4["커밋 4"] --> C5["커밋 5<br/>(오타 있는 설정 파일)"]
    C5 -- "git revert 커밋5" --> C6["커밋 6<br/>(커밋 5 내용을 취소)"]
</pre>

**두 번째 시행착오**는 revert 실행 후 자동으로 열린 커밋 메시지 편집 화면이었습니다. 이전에 `git commit`에서는 `-m` 옵션으로 메시지를 바로 넣는 것에 익숙해져 있어서, 편집기 화면이 뜨자 순간 멈춘 줄 알았습니다. Git이 기본 커밋 메시지("Revert 커밋5")를 미리 채워주니, 그대로 저장하고 편집기를 닫으면 된다는 걸 확인하고 나서야 해결됐습니다.

## 결과 (Result)

두 시나리오 모두 최종적으로는 원하는 상태로 되돌리는 데 성공했습니다.

|항목 | Before| After|
|---|---|---|
|로컬 커밋 (console.log)| 잘못된 코드가 포함된 커밋 1개| `--hard` 시행착오 1회 후, `--soft`로 정상 재커밋 완료|
|공유된 커밋 (오타 설정 파일)| 오타가 그대로 원격에 남아있음| `revert` 커밋 1개 추가로, 충돌 없이 취소 완료|
|팀원과의 충돌 발생 횟수| -| 0건 (revert로 처리했기 때문)|

가장 크게 배운 점은, **"되돌리고 싶다"는 목적이 같아도 그 커밋이 이미 공유됐는지에 따라 완전히 다른 명령어를 써야 한다**는 것이었습니다. 특히 `--hard` 옵션은 필요한 변경 내용까지 함께 날릴 수 있다는 걸 직접 겪어보고 나서야 왜 주의해야 하는 옵션인지 체감했습니다.

## 더 학습하면 좋은 개념

- **git reflog** — `reset --hard`로 사라진 것처럼 보이는 커밋도 사실 완전히 지워진 게 아니라, 일정 기간 `reflog`에 남아있어 복구할 수 있습니다. 실수했을 때 되돌릴 방법이 있다는 걸 알면 reset을 훨씬 덜 두려워하며 쓸 수 있습니다.
- **git cherry-pick** — revert가 "특정 커밋의 변경을 취소"하는 것이라면, cherry-pick은 반대로 "특정 커밋만 골라 다른 브랜치에 적용"합니다. 되돌리기와 짝을 이루는 개념이라 함께 익혀두면 좋습니다.
- **interactive rebase (`git rebase -i`)** — 여러 개의 커밋을 합치거나 순서를 바꾸는 등, 아직 공유하지 않은 기록을 더 정교하게 편집하는 방법입니다. reset보다 세밀한 "기록 다듬기" 도구입니다.
- **.gitignore** — 애초에 `console.log` 같은 디버깅 코드나 민감한 설정 파일이 커밋되지 않도록 예방하는 설정입니다. 되돌리기보다 예방이 항상 더 쉽다는 걸 이번 연습에서 느꼈습니다.
